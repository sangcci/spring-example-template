# Documentation Guide

## 작성 원칙

- 규칙, 적용 조건과 예외만 작성한다. 당위, 배경과 기대 효과는 생략한다.
- 같은 규칙은 원본 문서 한곳에 두고 다른 문서에서는 해당 섹션을 링크한다.
- 의미가 겹치는 문장과 항목은 통합한다. 본문, 표와 예시로 같은 내용을 반복하지 않는다.
- 예시만으로 규칙이 명확하면 설명을 붙이지 않는다. 예시에 드러나지 않는 조건과 예외만 덧붙인다.
- 업계에서 통용되는 용어로 긴 설명을 대체한다. 팀 고유 용어와 모호한 용어만 정의한다.
- 대상, 조건, 책임, 금지 사항과 승인 절차는 축약해도 유지한다.
- 작업 과정과 변경 이력은 Git history와 작업 기록에 남긴다.

## 형식과 예시

- 제목에는 순번을 쓰지 않는다. 번호 목록은 절차에만 사용한다.
- 판단 기준은 목록으로, 같은 기준의 비교는 표로 작성한다.
- 식별자, 경로, 명령과 설정값은 백틱으로 표시한다.
- 여러 줄 예시는 언어를 지정한 코드 블록으로 작성한다.
- 변경 전후 비교가 필요하면 같은 대상과 조건으로 보여준다. 권장 형태만으로 충분하면 해당 예시만 둔다.
- 실제 구현은 코드나 테스트 경로를 연결한다. 가상 예시는 현재 구현과 구분한다.
- 기술 예시는 코드와 SQL로, 업무 정책 예시는 조건과 결과로 표현한다.
- 이름, 기간과 기준값은 확정된 문서나 구현에서 확인한다. 예시로 새 정책을 만들지 않는다.

```java
// 비권장
String field = parameterName == null ? "request" : parameterName;

// 권장
String field = parameterName;
if (field == null) {
    field = "request";
}
```

## 문장과 용어

- 작업 지시는 독자를, 시스템 동작은 시스템을 주어로 쓴다.
- 능동형과 직접적인 동사를 사용한다.
- `적절히`, `필요시`, `관련 내용` 대신 대상과 조건을 명시한다.
- 같은 개념에는 같은 용어를 사용한다. 기술명과 제품명은 공식 표기를 유지한다.
- 익숙한 기술 용어와 약어는 풀어 쓰지 않는다.
- 가운데점 대신 쉼표, 접속사 또는 줄바꿈을 사용한다.

## 검토

- 중복과 불필요한 이유를 제거했는가?
- 예시가 전달하는 내용을 본문에서 반복하지 않았는가?
- 통용 용어로 대체할 수 있는 장황한 설명이 남았는가?
- 적용 조건, 예외, 책임과 승인 절차를 유지했는가?
- 문서와 구현의 차이를 임의 정책으로 채우지 않았는가?
- 원본 문서, 코드 경로와 섹션 링크가 유효한가?
