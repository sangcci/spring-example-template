# Policy Writing Guide

## 1. 문서의 역할

이 문서는 `docs/policies/`에 업무 정책서를 작성하는 기준을 정의한다. 정책서는 화면, API와 구현이 따라야 하는 업무 조건과 결과의 source of truth다.

정책서에는 업무 규칙을 작성한다. table, field, Java type, JWT claim, Redis key와 framework 설정 같은 구현 세부 사항은 architecture, security policy, API 문서 또는 코드에서 관리한다. 선택의 이유와 trade-off를 장기간 보존해야 하면 ADR을 작성한다.

## 2. 문서 구조

정책서의 대분류는 화면, API 또는 세부 기능이 아니라 업무 영역을 기준으로 나눈다. 관련 정책은 같은 업무 영역 아래에 모으고, 본문은 목차와 같은 순서로 배치한다.

문서 제목 바로 아래에 목차를 작성하며 별도의 목적 영역은 두지 않는다. 목차에는 업무 영역과 하위 항목을 표시하고 각 본문으로 이동하는 Markdown 링크를 연결한다.

```markdown
# Authentication Policy

## 목차

- [로그인](#로그인)
  - [인증 실패](#인증-실패)
- [인증 유지](#인증-유지)
  - [토큰 갱신](#토큰-갱신)

## 로그인

### 인증 실패

## 인증 유지

### 토큰 갱신
```

## 3. 참조형 구성과 읽는 순서

정책서는 이야기처럼 이어지는 서사형 문서가 아니라 필요한 정책을 빠르게 찾는 참조형 문서로 작성한다. 대분류는 업무 흐름에 따라 배치하되 각 영역은 다른 영역을 읽지 않아도 이해할 수 있어야 한다.

각 영역에는 핵심 정책을 먼저 작성하고 적용 조건, 예외와 적용 예시를 차례로 배치한다. 조건과 결과가 분명한 완결된 문장으로 작성하며 배경 설명과 연결 문장은 이해에 필요한 경우에만 사용한다.

## 4. 문장과 용어

모든 참여자가 같은 의미로 이해할 수 있는 업무 용어를 사용한다. 필드명, enum과 역할 코드 같은 구현 용어로 정책을 표현하지 않는다.

조건에 따른 판단, 동작, 허용 또는 제한은 조건을 먼저 제시한 서술형 문장으로 작성한다. 경우의 수가 많으면 같은 문장을 반복하지 않고 의사결정표를 사용한다.

미결정 사항이나 비교 대상은 길게 설명하지 않고 핵심 선택지를 `A vs B` 형식으로 작성한다.

```text
// 피한다
자동 로그인을 선택하지 않은 경우 세션을 하루 동안 유지할지 브라우저를 닫을 때 종료할지 아직 결정하지 않았습니다.

// 사용한다
일반 로그인 세션을 하루 동안 유지함 vs browser 종료 시 만료함
```

## 5. 정책 적용 예시

복잡하거나 오해하기 쉬운 정책에는 실제 서비스에서 정책이 어떻게 적용되는지 보여주는 예시를 둔다. 예시는 `text` 코드 블록 안에서 사례마다 번호를 매기고 `조건·행동 -> 정책 적용 결과` 순서로 작성한다.

````markdown
#### 적용 예시

```text
1. 등록되지 않은 이메일로 로그인 요청
   -> 계정 존재 여부를 노출하지 않는 인증 실패를 반환함

2. 사용한 refresh token을 다시 제출
   -> 같은 로그인에서 발급한 refresh session을 모두 폐기함
```
````

## 6. 권한 정책

역할별 허용 여부를 비교해야 하면 관련 영역 앞부분에 권한 매트릭스를 둔다. 기본 권한만 `허용`과 `불가`로 표시하고 조건과 예외는 표 아래에 서술한다.

## 7. 정책 상태

정책은 확정 여부와 반영 시점에 따라 다음 상태로 구분한다.

| 상태 | 정의 | 작성 형식 |
| --- | --- | --- |
| 정책 확정 | 결정이 완료되어 현재 적용하는 내용 | 관련 영역의 본문에 작성한다. |
| 논의 필요 | 현재 범위에서 결정해야 하는 내용 | 관련 영역 바로 아래에 `> 논의 필요`로 작성한다. |
| 추후 반영 예정 | 반영하기로 결정했지만 현재 범위에는 포함하지 않은 내용 | 관련 영역 바로 아래에 `> 추후 반영 예정`으로 작성한다. |
| 추후 검토 | 현재 범위 밖에서 도입 여부를 검토할 내용 | 관련 영역 바로 아래에 `> 추후 검토`로 작성한다. |

확정되지 않은 내용을 일반 정책과 섞지 않는다. 상태는 인용문 첫 줄에 고정 표제로 작성하고 다음 줄부터 내용을 작성한다.

```markdown
> 논의 필요
>
> 일반 로그인 세션을 하루 동안 유지함 vs browser 종료 시 만료함
```

## 8. 다른 문서와의 경계

- 업무 조건과 사용자가 관찰하는 결과는 정책서에 작성한다.
- API의 request, response, HTTP status와 field 계약은 API 문서에 작성한다.
- security protocol, token 검증, cookie와 암호화 기준은 `docs/security-policy.md`에 작성한다.
- architecture 선택의 맥락, 대안과 철회 조건은 ADR에 작성한다.
- 같은 내용을 여러 문서에 복제하지 않고 source of truth를 링크한다.

정책과 구현이 다르면 현재 동작을 정책처럼 정당화하지 않는다. 차이를 드러내고 확정된 결정에 따라 정책 또는 구현을 함께 갱신한다. AI agent는 `논의 필요`와 문서의 빈틈을 임의의 안전장치나 업무 규칙으로 채우지 않는다.
